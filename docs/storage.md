# Хранение и размещение

Приложение хранит карты в IndexedDB текущего браузера, без аккаунта и внешних запросов с данными карт. Для размещения достаточно статического HTTPS-хостинга: Cloudflare Pages, GitHub Pages, Netlify, Vercel или собственного nginx. Ключи API и сервер не нужны. Каталог сборки — `dist`; HTTPS нужен для Service Worker и Web Crypto.

IndexedDB привязана к origin (протокол, домен и порт), профилю браузера и устройству. Это не облачная синхронизация. Смена домена, очистка данных сайта, приватный режим или удаление браузера могут привести к потере карт. `navigator.storage.persist()` может уменьшить риск автоматического удаления данных браузером, но предоставление постоянного хранилища решает браузер. Пользователь должен сохранять резервные копии отдельно.

Открытая JSON-копия удобна для переноса, но содержит номера карт в читаемом виде. Парольная копия использует AES-256-GCM, свежие случайные salt (16 байт) и IV (12 байт), ключ из PBKDF2-SHA-256 (600 000 итераций). Пароль не сохраняется, восстановить забытый пароль нельзя. Локальная IndexedDB не зашифрована: защита резервной копии не является блокировкой самого приложения. Экспортированный шифротекст можно хранить в личном облаке или файловом архиве.

Импорт проверяет версию формата, типы полей, уникальность ID, ограничения длины, цвета и EAN-13 checksum. Максимум 1000 карт и 8 МБ на файл. Параметры шифрования принимаются только в поддерживаемом виде, чтобы файл не мог навязать чрезмерную вычислительную нагрузку. Неизвестные поля отбрасываются. Запись в IndexedDB подтверждается только после завершения транзакции; ошибка не должна отображаться в UI как успешное сохранение.

Перед обычным сохранением приложение сравнивает текущие данные IndexedDB со снимком последней загрузки в той же транзакции записи. Если другая вкладка уже изменила карты, сохранение отклоняется с предложением перезагрузить страницу. Это защищает чужие изменения от перезаписи устаревшим состоянием. После повреждения хранилища доступна отдельная явная операция восстановления с заменой данных; обычное редактирование после ошибки загрузки запрещено.

Номер сохраняется строкой, включая ведущие нули. CODE128 ограничен 80 печатными ASCII-символами. Для QR действует ограничение 1024 символа и 2000 байт UTF-8: многобайтный текст проверяется по реальному размеру, чтобы сохранённую карту можно было отобразить в QR с уровнем коррекции M.

## Если понадобится синхронизация

Практичный следующий шаг — пользовательская авторизация и таблица в Supabase с RLS, где чтение и запись разрешены только владельцу записи. Публичный клиентский publishable key не заменяет RLS; service-role key никогда не попадает в браузер. Альтернатива без собственного backend — пользовательский WebDAV с явным вводом credentials и настроенным CORS, но совместимость провайдеров придётся проверять, а конфликты версий решать отдельно. В текущей версии удалённая синхронизация не реализована. Для небольшого набора карт IndexedDB и переносимые резервные копии дают меньше зависимостей и проще развёртываются.

Источники: [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API), [PBKDF2 deriveKey](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/deriveKey), [Web Cryptography specification](https://www.w3.org/TR/webcrypto/), [постоянное хранилище браузера](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist), [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
